> 核对日期：2026-09-15  
> 仓库：https://github.com/mattpocock/skills  
> 插件版本：`1.2.3`  
> 许可证：MIT

`mattpocock/skills` 不是代码生成框架，也不是可以独立运行的软件。它是一组写给 AI 编程代理阅读的 Markdown 工作流，用 `SKILL.md` 约束代理在澄清、规格、拆单、实现、测试、审查、故障诊断和架构巡检中的行为。

它的核心不是让代理多写代码，而是让它更早澄清问题、把决定留在仓库、用反馈回路验证结果，并把技能设计成小而可组合的模块。它适合希望保留工程控制权、又不愿每次从零编写提示词的开发者。

## 安装与维护方式

Claude Code 官方插件：

```bash
claude plugins install mattpocock-skills
```

也可以在 Claude Code 会话中执行：

```text
/plugin install mattpocock-skills
```

Codex 和其他支持 Agent Skills 的工具：

```bash
npx skills@latest add mattpocock/skills
```

只安装单个技能或更新技能：

```bash
npx skills@latest add mattpocock/skills --skill=<name>
npx skills@latest update <name>
```

安装时请确保选择 `setup-matt-pocock-skills`，否则部分工程技能无法完成仓库初始化。

Claude Code 插件和 `skills.sh` 是两条互斥路线。前者托管、只读并自动更新；后者把可编辑的 Markdown 复制到项目中，适合自行修改。同时安装会出现两套同名技能。

MIT 许可证允许修改和再分发，但应保留许可证文本和版权声明。

## 仓库结构与 setup

当前版本约有 155 个文件、35 个 `SKILL.md`。插件清单列出 25 个正式技能，即 18 个工程技能和 7 个生产力技能。

```text
skills/
  engineering/      正式工程技能
  productivity/     通用生产力技能
  misc/             未随插件正式发布的补充技能
  in-progress/      实验中的技能
docs/
  engineering/      正式工程技能的详细说明
  productivity/     生产力技能的详细说明
.agents/
  invocation.md     用户调用与模型自动调用的规则
  install-block.md  安装文案的单一来源
.claude-plugin/
  plugin.json       Claude Code 插件清单
  marketplace.json  备用插件市场配置
```

每个正式技能通常包含 `SKILL.md`、`agents/openai.yaml`，以及按需提供的模板、脚本和参考资料。`SKILL.md` 定义行为，`agents/openai.yaml` 提供 Codex 侧的显示名称、简述和调用策略。

### 每个仓库运行一次 setup

安装后，在需要启用工程流程的仓库中运行：

```text
/setup-matt-pocock-skills
```

Codex 中也可以使用 `$setup-matt-pocock-skills` 或自然语言请求。这个技能只确认三件事：

1. issue tracker 在哪里。
2. triage 标签如何映射。
3. 领域文档放在哪里。

它会读取 `git remote`、已有的 `CLAUDE.md`、`AGENTS.md`、`CONTEXT.md`，以及 monorepo 或多上下文目录信号。确认后通常写入：

```text
docs/agents/issue-tracker.md
docs/agents/domain.md
docs/agents/triage-labels.md    # 安装了 triage 时
```

它还会尽量在已有指令文件中加入 `## Agent skills`。配置只作用于仓库，不写入用户全局目录，因为不同项目的 tracker 和标签体系可能不同。

| tracker | issue 存放位置 | 需要 |
| --- | --- | --- |
| GitHub | GitHub Issues | `gh` CLI |
| GitLab | GitLab Issues | `glab` CLI |
| 本地 Markdown | `.scratch/<feature>/` | 无远程仓库也可以 |
| 其他 | 由你描述 | 明确的工作流说明 |

Linear、Jira、Azure DevOps 等可通过“其他”模式接入。技能读取 `docs/agents/issue-tracker.md` 后再决定如何查找和更新 issue，并不硬编码 GitHub。

setup 只写标签映射，不创建标签。新仓库需要在 tracker 中准备 `bug`、`enhancement`、`needs-triage`、`needs-info`、`ready-for-agent`、`ready-for-human`、`wontfix`；使用 wayfinder 时还要准备 `wayfinder:map`、`wayfinder:grilling`、`wayfinder:prototype`、`wayfinder:research`、`wayfinder:task`。

Codex 用户还要检查 `CLAUDE.md` 与 `AGENTS.md` 的优先级。setup 的规则是“存在 `CLAUDE.md` 就编辑它，否则编辑 `AGENTS.md`”。如果 Codex 实际读取的是 `AGENTS.md`，新增区块可能落进不被读取的文件。应手动移动该区块，或让 `AGENTS.md` 成为唯一事实来源。

## 调用模型与 25 个正式技能

技能最重要的设计轴是“谁能调用”。

`User-invoked` 只能由人主动调用，通常负责编排流程。Claude Code 使用 `disable-model-invocation: true`，Codex 在 `agents/openai.yaml` 中使用：

```yaml
policy:
  allow_implicit_invocation: false
```

`Model-invoked` 可以由人或模型调用，通常承载可复用纪律。用户调用型技能可以调用模型调用型技能，但用户调用型技能之间不能互相调用。

| 工具 | 常见调用方式 |
| --- | --- |
| Claude Code | `/skill-name` |
| Codex | `$skill-name` 或自然语言描述任务 |
| 其他 Agent Skills 工具 | 技能选择器、Skill 工具或自然语言触发 |

README 中的 `/skill-name` 主要沿用 Claude Code 表达。在 Codex 中可以直接说“用 `diagnosing-bugs` 调查这个间歇性失败”，或使用 `$diagnosing-bugs`。自动调用是否发生仍取决于 harness、模型、技能描述和全局指令。

### 正式技能清单

| 技能 | 调用类型 | 解决的问题 | 主要产物或行为 |
| --- | --- | --- | --- |
| `ask-matt` | User | 不知道该用哪个技能 | 只给出下一步输入，不替用户执行 |
| `grill-with-docs` | User | 计划模糊，项目术语不稳定 | 盘问并持续更新 `CONTEXT.md` 与 ADR |
| `triage` | User | 外部 issue 或 PR 混乱 | 分类、验证、追问、写 agent brief、更新标签 |
| `improve-codebase-architecture` | User | 代码库逐渐变浅、变乱 | 生成架构巡检 HTML，再选择候选深入讨论 |
| `setup-matt-pocock-skills` | User | 工程技能不知道 issue 和文档在哪里 | 每仓库运行一次，写入 `docs/agents/*` |
| `to-spec` | User | 决定需要跨多个 session 保存 | 把当前对话合成为 tracker 中的 spec |
| `to-tickets` | User | 规格太大，需要执行切片 | 生成垂直切片和带 blocking edges 的工单 |
| `implement` | User | 工作已经决定，需要落地 | 读取 spec 或 ticket，驱动 TDD、检查、审查并提交 |
| `wayfinder` | User | 工作大到单 session 装不下，路线仍不明 | 在 tracker 上建立决策地图并逐个消除未知 |
| `prototype` | Model | 设计问题靠讨论无法决定 | 一次性 HTML 逻辑原型或多套 UI 变体 |
| `diagnosing-bugs` | Model | 难 bug、间歇失败、性能回退 | 先建立会变红的反馈回路，再最小化、假设、插桩、修复 |
| `research` | Model | 下一步卡在外部事实 | 查一手来源，留下带引用的 Markdown |
| `tdd` | Model | 需要用测试约束行为 | 单条失败测试到最小实现，按垂直切片推进 |
| `domain-modeling` | Model | 项目术语模糊或冲突 | 挑战术语，更新 `CONTEXT.md` 和 ADR |
| `codebase-design` | Model | 需要讨论模块形状 | 提供 deep module、interface、seam 等共享词汇 |
| `code-review` | Model | 一个 diff 需要审查 | 分开执行 Standards 与 Spec 两条审查轴 |
| `resolving-merge-conflicts` | Model | merge 或 rebase 停在冲突中 | 追溯两边意图，检查并完成提交，不 abort |
| `wizard` | Model | 必须人工点击控制台或录入密钥 | 生成由人运行的交互式 bash wizard |
| `grill-me` | User | 任意领域的想法还站不住 | 无状态盘问，不写文件，适合非代码场景 |
| `handoff` | User | 工作要跨 session、目录、工具或同事 | 在临时目录生成轻量交接文档 |
| `teach` | User | 要长期学习一个主题 | 建立 mission、resources、HTML 课程和 learning records |
| `to-questionnaire` | User | 决定依赖另一个人掌握的知识 | 生成可直接发送的 Markdown 问卷 |
| `wait-what` | User | 上一条消息没听懂 | 用更短表达补足前提并重新讲一遍 |
| `grilling` | Model | 需要可复用的盘问原语 | 按 frontier 逐轮提问，问题之间不互相依赖 |
| `writing-for-agents` | Model | 写给代理的文档冗长、重复、含糊 | 删除无操作词句，让代理稳定执行同一过程 |

## 四条主要工作流

### 多 session 的新功能

适合已经决定要做、但无法在一个上下文窗口完成的工作：

```text
想法
  -> /grill-with-docs
  -> /to-spec
  -> /to-tickets
  -> 每个 ticket 单独 /implement
  -> /code-review
```

推荐让 `grill-with-docs`、`to-spec`、`to-tickets` 在同一个连续上下文中完成。`to-spec` 到 `to-tickets` 之间不要 clear 或 compact，否则大型 spec 可能需要重新读取，甚至被截断。发布工单前要检查切片粒度、blocking edges 和合并需求；每张 ticket 使用新的上下文，并确认 `implement` 提交到正确分支。

这条流程的价值不是“多写文档”，而是让决定跨上下文存活。

### 单个 session 就能完成的改动

如果计划已经清楚，或者当前对话足以让代理完成实现，不必为了形式补 spec 和 tickets：

```text
/grill-with-docs
  -> /implement
```

很小的改动可以直接描述任务；但涉及多个隐含决定、公共接口或测试 seam 时，仍应先澄清。`to-spec` 的触发条件是“工作跨多个 session”，不是“任何功能都必须先写规格”。

### 处理别人提交的 issue

```text
/triage
  -> 验证、分类、追问或写 agent brief
  -> /implement
```

`triage` 只处理外部进入的 issue 或外部 PR，不用于 `to-tickets` 自己生成的工单。它会为每个条目确定类别角色 `bug` 或 `enhancement`，以及状态角色 `needs-triage`、`needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。

给出 agent brief 前，它会尽量复现 bug、checkout 并运行外部 PR、检查功能是否已经存在，以及概念是否已被 `.out-of-scope/` 拒绝。原始 report 只是背景，brief 才是后续实现契约。

### 超大且路线不明的项目

```text
/wayfinder
  -> 建立 map 和 decision tickets
  -> 一次解决一个 ticket
  -> /to-spec #<map_issue>
  -> /to-tickets
  -> /implement
```

Wayfinder 的 ticket 是决策 ticket，不是实现 ticket。

| 类型 | 模式 | 用途 |
| --- | --- | --- |
| `wayfinder:grilling` | HITL | 讨论就能解决的决策 |
| `wayfinder:prototype` | HITL | 必须看到原型才能回答的设计问题 |
| `wayfinder:research` | AFK | 外部事实阻塞决定，可后台并行研究 |
| `wayfinder:task` | 两者皆可 | 阻止决策的人工任务，例如开通权限 |

map 清空后不能直接把它当成实现计划。它仍然只是一个带链接的决策集合，需要 `to-spec` 收敛成可构建文档。

## 从想法到可审查提交

以“给 SaaS 增加团队级审计日志”为例，先运行 `/grill-with-docs`。代理应澄清日志属于组织、团队还是用户，谁能查看、保留多久、删除内容如何表示，以及“成员”“用户”“账号”是否为同一概念。已确定的术语写入 `CONTEXT.md`，难以逆转的决定写入 ADR。

如果两天内、一个上下文里能完成，直接运行 `/implement`。若涉及数据库迁移、查询 API、权限模型、前端页面、导出任务和多个测试层，则运行 `/to-spec`。`to-spec` 不重新盘问，而是把已决定的对话整理成 issue；写正文前应先确定测试 seam，因为后续 `tdd` 和 `code-review` 都依赖它。

接着用 `/to-tickets` 拆成 tracer-bullet tickets。好的 ticket 是一条很窄、但贯穿所有层的完整路径：

```text
记录一条最基础的团队审计事件，并能通过最小查询接口读回。
```

按“建表、写 API、写页面、补测试”分层拆开通常不合适，因为前三项都无法单独演示，测试也只能在最后才有意义。每张 ticket 应回答：完成后能演示什么，受哪些 ticket 阻塞，以及全新 session 能否只看这张 ticket 就完成。

逐张执行 `/implement #123`，每张使用新的上下文。`implement` 通常读取 ticket 或 spec、复述实现内容、在约定 seam 上调用 `tdd`、运行类型检查和相关测试、调用 `code-review`，最后提交当前分支。之后仍可独立运行 `/code-review main`，分别查看 Standards 与 Spec。两条轴不能互相抵消：代码规范但做错事，和功能做对但破坏仓库标准，是两类不同问题。

## 按场景选择技能

| 场景 | 首选 | 关键边界 |
| --- | --- | --- |
| 不知道该用什么 | `/ask-matt` | 只推荐下一步，只了解该仓库的正式技能 |
| 非代码仓库中的模糊想法 | `/grill-me` | 不需要仓库，不写文件 |
| 代码仓库中的模糊计划 | `/grill-with-docs` | 能读代码，并把结论写入 `CONTEXT.md` 与 ADR |
| 缺少外部事实 | `/research` | 问题要窄，并给出一手来源引用 |
| 讨论无法确定设计 | `/prototype` | 只回答一个问题；原型放在 `prototype/<name>` 分支，不合并 main |
| 复杂 bug | `/diagnosing-bugs` | 第一阶段必须建立已经失败、修复后会通过的反馈回路 |
| 架构腐化 | `/improve-codebase-architecture` | 只巡检并生成报告，不改代码；候选再走 grill、spec、tickets、implement |
| 人工控制台或密钥 | `/wizard` | 代理只写脚本，由人运行；密钥不要粘贴进聊天 |
| merge 或 rebase 冲突 | `/resolving-merge-conflicts` | 追溯两侧 commit、PR 或 issue 意图，不简单选择 ours 或 theirs |
| 上一条消息没讲清 | `/wait-what` | 补足缺失前提，用项目词汇重讲，不是单纯缩短 |
| 下一步取决于另一个人 | `/to-questionnaire` | 先明确发给谁和需要对方返回什么 |
| 长期学习 | `/teach` | 使用独立目录；课程引用来源，并推荐可阅读的一手资料 |

如果只安装五个技能，可以按目标选择：

| 目标 | 五个技能 |
| --- | --- |
| 个人开发功能 | `setup-matt-pocock-skills`、`grill-with-docs`、`implement`、`tdd`、`code-review` |
| 维护开源项目 | `setup-matt-pocock-skills`、`triage`、`diagnosing-bugs`、`implement`、`code-review` |
| 接手陌生代码库 | `setup-matt-pocock-skills`、`grill-with-docs`、`improve-codebase-architecture`、`codebase-design`、`diagnosing-bugs` |
| 非代码用途 | `grill-me`、`research`、`wait-what`、`to-questionnaire`、`teach` |

## 协作规则与已知限制

要稳定使用这套技能，应遵守以下边界：

1. 先运行 setup。`to-spec`、`to-tickets`、`triage`、`wayfinder` 和 `implement` 都依赖 tracker 配置。
2. 不要把 `implement` 当成重新设计。它会高效执行一个未经澄清的错误方案。
3. 在 `to-spec` 阶段谈好测试 seam。拖到 `implement` 或 `tdd` 才讨论通常已经太晚。
4. 保持上下文边界。澄清、spec、tickets 尽量连续；每个实现 ticket 使用新上下文。
5. 一个 wayfinder HITL ticket 一个 session。并行 session 看不到彼此回答，容易重复提问或形成冲突决定。
6. research 问题要窄。范围越大，越容易耗尽 token、重复委派后台代理，却漏掉关键细节。
7. prototype 只回答一个问题，避免因为惯性让原型直接变成生产代码。
8. 不要把 `triage` 用在 `to-tickets` 生成的工单上，那些工单已经带 ready 状态和 brief。
9. 改动最好由最了解它的 session 完成合并，避免后续代理只能从 commit 和 issue 重新推断意图。

以下是当前版本和流程中最值得注意的限制：

| 范围 | 限制 | 应对 |
| --- | --- | --- |
| setup 标签 | 只写映射，不创建 tracker 标签 | 首次使用前手工建立所需标签 |
| 长 spec | tracker 可能无法完整、干净地返回大型 spec | `to-spec` 后立即 `to-tickets`，中间不要 clear 或 compact |
| 工单拆分 | 模型容易拆得过细，GitHub sub-issue 和 blocking link 也可能创建失败 | 人工检查垂直路径，必要时用 `gh issue edit <parent> --add-sub-issue <child>` 和 `gh issue create --blocked-by <issue>` 补齐 |
| TDD 语义 | 当前技能是 red-green，独立的 refactor 阶段已移除，重构交给 `code-review` | 需要 classic TDD 时自行扩展；描述中的 red-green-refactor 只是一致触发短语 |
| research | 子代理可能继续生成子代理，产生重复后台任务 | 调用后检查后台任务，重复时手动停止；结果必须由后续流程显式引用 |
| 架构报告 | HTML 可能从 CDN 加载样式和图表 | 离线或严格 CSP 环境要求内联 CSS，并使用手写 SVG |
| teach | `./` 路径存在歧义，课程可能写入技能安装目录；测验答案位置也可能单一 | 开始前明确学习工作区；不要把选项位置当提示 |
| wizard | bash wizard 单向前进，输入错误通常要 Ctrl-C 重跑，部分终端不支持方向键编辑 | 预留重跑成本；不要把密钥粘贴进模型上下文 |
| wayfinder | 容易从规划滑向实现，`wayfinder:task` 可能变成一块产品工作 | 持续确认 ticket 仍是问题，Notes 没有绕过批准的边界 |
| 模型差异 | 不同模型和 harness 对 subagent、后台任务、自动调用支持不同，技能不是运行时保证 | 把技能当作默认质量约束，并检查实际行为 |


## 结语

这套技能适合已经认可工程纪律、但希望把这些纪律更稳定地注入 AI 编程流程的人。优势在于动手前澄清、把知识落到仓库、用反馈回路约束实现，并让结果更容易审查和接手。

它的成本同样明确：会引入文档和流程，对 issue tracker、分支和上下文卫生有要求，并依赖模型与 harness 配合。如果你的目标是“一句话自动做完整个项目”，它并不合适；如果目标是让代理成为有纪律、但仍由人掌握决定的工程协作者，它值得研究。

实际采用时，建议从 `mattpocock/skills` 安装少量技能，在目标仓库运行一次 setup，再用一个边界清楚的功能验证整条流程。确认收益后，再逐步扩大到团队约定。
